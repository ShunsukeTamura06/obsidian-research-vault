# 設計思想 — なぜ LLM Wiki なのか

## 問題

LLM を使った知識管理の主流は RAG（Retrieval-Augmented Generation）。
ファイルをアップロードし、質問のたびにベクトル検索でチャンクを引き、回答を合成する。

これには根本的な限界がある:

> **毎回ゼロから知識を再発見する。蓄積がない。**
> 5 つの文書を統合する必要がある質問は、毎回 5 つを探して繋ぎ直す。

— Andrej Karpathy, [LLM Wiki Gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

## 解決策

合成を **クエリ時** ではなく **取り込み時** に行う。
取り込まれたソースは、Claude が:

1. 既存の wiki ページに影響する箇所を探し
2. それらを更新し
3. 新しい概念があればページを作る

結果として、`wiki/` は **時間とともに賢くなる**。1 つのソースが 10 〜 15 ページに
影響を与えるので、ソースが増えるほどクロスリファレンスが密になる。

> "Obsidian は IDE、LLM はプログラマ、wiki はコードベース"
> — Karpathy

## 3 層アーキテクチャ

```
┌──────────────────────────────────────┐
│ CLAUDE.md (Schema)                   │  ← 振る舞いの規定
│  - フォルダの責務                    │
│  - 出力フォーマット                  │
│  - 処理プロトコル                    │
└──────────────────────────────────────┘
            ↓ 規定する
┌──────────────────────────────────────┐
│ wiki/ (Synthesis / Compounded)       │  ← Claude が育てる
│  - 概念ページ                        │
│  - 銘柄・人物ページ                  │
│  - 相互リンク                        │
└──────────────────────────────────────┘
            ↑ 合成する
┌──────────────────────────────────────┐
│ raw/ (Immutable Sources)             │  ← 原文。読むだけ
│  - 記事、PDF、議事録                 │
│  - 適時開示、決算短信                │
└──────────────────────────────────────┘
```

## 何が普通の Obsidian 運用と違うか

- **生資料と合成資料を物理的に分離** — raw/ は不変、wiki/ は流動
- **メンテナンスを LLM に委譲** — 人間がやらない 50 ファイルの相互リンク更新を Claude が担う
- **CLAUDE.md が運用ルール** — チャットの場当たり指示でなく、永続的な規約

## 過信しないために

- これは個人〜小チーム向けのパターン。**組織全体の DB として安易に拡張しない**
- 最初の 2 週間は wiki がぐちゃぐちゃになる。**iterate を前提とする**
- LLM の出力は常にレビュー対象。**特に数値と固有名詞**
- 機密情報は raw/ に入れたが最後、wiki に漏れるリスクがある。
  本テンプレートの `.gitignore` は raw/ を除外しているが、
  実運用ではアクセス制御も含めて設計すること。
